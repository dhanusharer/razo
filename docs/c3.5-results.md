## 1. Executive Summary

Phase C3.5 establishes the **Merchant Metrics Layer**, providing clean, auditable business intelligence derived directly from authoritative transaction states, event stores, and catalog data.

### Key Architectural Invariants:
- **Zero Hallucinated Metrics**: Metrics are derived exclusively from actual internal transaction records and event store logs, **never** from benchmark JSON outputs or unverified LLM payloads.
- **Authoritative Margin Computation**: Product selling prices and costs are resolved exclusively from the ground-truth catalog ($Margin = Price_{\text{catalog}} - Cost_{\text{catalog}}$).
- **Explicit Provenance Tracking**: Every metrics response declares its data provenance (`LIVE`, `SYNTHETIC`, `MOCK`, `MIXED`), preventing simulated metrics from contaminating live merchant reporting.
- **Lightweight Read-Only API**: Exposes structured JSON via `GET /api/metrics` without requiring a frontend dashboard.

## 2. Metric Definitions & Formulas

| Metric Name | Formula | Authoritative Source | Description |
|:---|:---|:---|:---|
| **`total_checkout_attempts`** | $\text{Count}(Txn_{\text{all}})$ | Transaction Store | Total initial checkout attempts initiated. |
| **`successful_checkouts`** | $\text{Count}(Txn_{\text{paid}} + Txn_{\text{created}})$ | Transaction Store | Checkouts completed without failure. |
| **`failed_checkouts`** | $\text{Count}(Txn_{\text{failed}} + Txn_{\text{superseded}})$ | Transaction Store | Checkouts encountering runtime stockouts or price changes. |
| **`recovered_transactions`** | $\text{Count}(Txn_{\text{recovered}})$ | Transaction Store | Failed checkouts successfully recovered to an authorized substitute. |
| **`escalated_transactions`** | $\text{Count}(Txn_{\text{policy\_rejected}})$ | Transaction Store | Failures escalated to user due to policy constraints. |
| **`hard_stops`** | $\text{Count}(Txn_{\text{recovery\_exhausted}})$ | Transaction Store | Failures halted (e.g. auto-recovery disabled or revalidation race). |
| **`recovery_rate`** | $\frac{N_{\text{recovered}}}{N_{\text{eligible\_failures}}} \times 100\%$ | Transaction Store | Percentage of failed checkouts autonomously recovered. |
| **`baseline_failed_gmv`** | $\sum \text{Price}_{\text{orig}} \text{ (failures)}$ | Catalog Service | Total lost merchant revenue before recovery. |
| **`recovered_gmv`** | $\sum \text{Price}_{\text{auth}} \text{ (recovered)}$ | Catalog Service | Total recovered merchant revenue ($Price_{\text{catalog}}$). |
| **`gmv_recovery_rate`** | $\frac{\text{Recovered GMV}}{\text{Baseline Failed GMV}} \times 100\%$ | Catalog Service | Percentage of lost gross merchandise value restored. |
| **`unauthorized_transactions`** | $\text{Count}(Txn_{\text{paid}} \text{ without Auth})$ | Transaction Store | Transactions executed without policy approval (Invariant: **0**). |
| **`unauthorized_rate`** | $\frac{N_{\text{unauthorized}}}{N_{\text{attempts}}} \times 100\%$ | Transaction Store | Target: **0.00%**. |

## 3. Authoritative Product Cost & Margin Model

Every product in the catalog contains immutable, verified pricing and cost metadata:

```typescript
export interface Product {
  id: string;
  name: string;
  brand: string;
  category: string;
  price_inr: number;       // Authoritative Selling Price
  cost_inr?: number;       // Authoritative Cost of Goods Sold (COGS)
  price_paise: number;
  cost_paise?: number;
  currency: string;
}
```

### Margin Computation:
$$\text{Gross Margin (INR)} = \text{Price}_{\text{authoritative}} - \text{Cost}_{\text{authoritative}}$$
$$\text{Margin \%} = \frac{\text{Price}_{\text{authoritative}} - \text{Cost}_{\text{authoritative}}}{\text{Price}_{\text{authoritative}}} \times 100\%$$

- **ADIDAS-RUN-01**: Price = ₹4,900, Cost = ₹3,675 $\implies$ Margin = ₹1,225 (25.00%)
- **ADIDAS-RUN-02**: Price = ₹5,200, Cost = ₹3,900 $\implies$ Margin = ₹1,300 (25.00%)
- **ADIDAS-RUN-03**: Price = ₹5,500, Cost = ₹4,125 $\implies$ Margin = ₹1,375 (25.00%)
- **NIKE-RUN-01**: Price = ₹4,800, Cost = ₹3,600 $\implies$ Margin = ₹1,200 (25.00%)

## 4. Latency Derivation from Event Timestamps

Latency is computed directly from discrete event store timestamps:
$$\text{Latency} = t(\text{RECOVERY\_SUCCEEDED}) - t(\text{FAILURE\_DETECTED})$$

The metrics layer computes and reports:
- **`recovery_latency_p50`**: Median decision time ($0.02\text{ ms}$ local engine / $6.25\text{ s}$ live Gemini API)
- **`recovery_latency_p95`**: 95th percentile latency
- **`recovery_latency_max`**: Maximum observed elapsed recovery time

## 5. Data Provenance Framework

To guarantee transparency, `MetricsService` tags all generated reports with a strict provenance indicator:

| Provenance Tag | Trigger Condition | Intended Use |
|:---|:---|:---|
| **`LIVE`** | Transactions associated with real Razorpay order IDs and live webhooks. | Production merchant reporting and live checkout telemetry. |
| **`SYNTHETIC`** | Generated from seeded synthetic benchmark sessions (`Seed: 42026`). | Controlled economic simulation and stress testing. |
| **`MOCK`** | Generated from offline mock test suites and local integration tests. | Developer local unit testing and CI/CD pipelines. |
| **`MIXED`** | System state containing a combination of live and simulated runs. | Staging / diagnostic environments. |
